# Decisions

| # | Decision | Why | Status |
|---|---|---|---|
| D1 | Stack: FastAPI, SQLAlchemy 2, Pydantic, PostgreSQL | Owner decision. Not rewriting into Node | Final |
| D2 | Chatwoot is the inbox; native Meta Cloud API; native campaigns kept; no Kapso; no custom campaign system | Owner decision | Final |
| D3 | n8n is staff-only; money, wallet and authorization stay in the hub | Owner decision | Final |
| D4 | WiseCP owns subscriptions and payments; hub owns wallet, usage, AI allowance. No customer-pays-Meta fallback | Owner decision | Final |
| D5 | Money is integer minor units; pricing uses Decimal; ceil rounding on Meta cost and on charge | Avoids float drift; never undercharge by rounding | Implemented, tested |
| D6 | Idempotency by unique DB key on the ledger (`idempotency_key`), claimed inside a savepoint before the balance moves | Concurrent duplicates cannot double-apply | Verified on PostgreSQL (tests/test_postgres.py) |
| D7 | Balance moves with one conditional `UPDATE ... WHERE balance >= amount` | Concurrent spenders cannot overspend | Verified on PostgreSQL |
| D8 | Alembic owns the schema. `create_all` only when ENV=development | Spec 2.4 | Implemented |
| D9 | Production refuses to boot without PostgreSQL, a 32+ char secret and Chatwoot settings | No silent SQLite or default secret | Implemented, tested |
| D10 | Baseline migration 0001 may be regenerated until the first real deployment, because Phase 2/3 reshape the schema. After first deploy, migrations are append-only | Nothing is in production yet | Open until first deploy |
| D11 | Hosting: Docker (Coolify) with a PostgreSQL container, not OpenPanel | Python service plus Postgres needs process, env, health and rollback management that a PHP panel does not give | Recommended, pending owner confirmation |

| D12 | Lifecycle: pending, provisioning, provisioning_failed, active, suspended, cancelling, cancelled, terminated. Only moves in `lifecycle.TRANSITIONS`. Cancelled tenants are never reactivated by `unsuspend`; there is no reactivation in Phase 2 | Spec 5; closes the audited defect | Implemented, tested |
| D13 | Plans and per-tenant entitlements live in the DB. Overrides, paid add-ons and free grants are separate columns; every change is audited with before/after | No hard-coded plan or markup constants | Implemented |
| D14 | Chatwoot work runs as PostgreSQL jobs (SKIP LOCKED + lease + backoff). Handlers apply the tenant's *current* desired state | Resumable, order-independent, no Redis | Implemented, tested |
| D15 | If a Chatwoot create call has an ambiguous outcome (timeout/5xx), the job BLOCKS for an operator. Retry needs `chatwoot_account_id` (adopt) or an explicit `confirm_not_created` | A blind retry could create a duplicate account | Implemented, tested |
| D16 | Internal credentials are bound to tenants in `api_key_tenants`. The credential decides the tenant; a supplied id may only select among bound tenants. Unbound = no access. Not-yours answers 404 | Closes the audited cross-tenant defect | Implemented, tested |
| D17 | Terminate never deletes Chatwoot data | Retention policy not defined | Implemented |
| D18 | Billing periods are calendar months in Africa/Lagos; timestamps stored UTC | Owner decision | Implemented, tested |
| D19 | APPROVED, NOT BUILT: bounded overdraft. Pre-send needs funds or an explicit credit limit (default 0) via atomic reservations; Meta charges already incurred are recorded and the shortfall becomes a receivable; `allow_negative` is not a general way to authorise sends; ingestion continues when suspended | Owner decision | Phase 3 |
| D20 | Customer auth targets Citichoice account SSO behind an `IdentityProvider` interface; dev adapter only outside production | Owner decision; protocol unverified | Interface done, adapter pending |
| D21 | Staff sign in with Zitadel OIDC (own application, Authorization Code + PKCE, confidential client). Roles read from the ID token; the `administrator` role is enforced on EVERY /ui route per request, not only at login. No tokens are stored, only a hashed session id | Owner decision; Cloudflare Access and Zitadel are extra layers, not substitutes | Built; mock-IdP tested; live checklist pending |
| D22 | Two hostnames. `deskhub.*` serves only /ui and /auth; `hub.*` serves only the machine API. API keys are for services (WiseCP, n8n), never people | A rule on one host cannot be bypassed through the other | Built, tested |
| D23 | Customer routes and the signed usage page are OFF by default (`CUSTOMER_API_ENABLED=false`); membership tables kept | Owner decision: admin-only first release | Built, tested |
| D24 | Money is stored as BIGINT micro-units (10^-6 of the currency's major unit), each row carrying its ISO 4217 code. A DB foreign key forces ledger entries to match their wallet's currency | Sub-cent message costs; WiseCP's 4-decimal amounts convert exactly; no floats anywhere | Built; PostgreSQL migration tested with legacy data |
| D25 | Currency exponents follow ISO 4217 (not CLDR, which differs for IQD, ALL, LAK and others). Codes WiseCP knows that are not in the current ISO list are flagged and cannot be used for billing until staff enable them | Verified against your 166 WiseCP currencies | Built |
| D26 | Billing in a currency must be switched on by staff (audited). A tenant's wallet currency = its WiseCP billing currency and is never silently reinterpreted | Owner requirement | Built |
| D27 | FX source for pricing: read WiseCP's current currency rates (it already runs exchangerate-api.com) and snapshot them in the hub; do not subscribe to a second rate service | Avoids a second authority | Planned (3.3) |
| D28 | Wallet credit from a top-up = the line's subtotal EXCLUDING tax | Owner decision (VAT never enters the wallet) | Contract documented; built in Phase 4 |
| D29 | Rate cards: per provider, category, market and BILLING currency, windows [from, to), versioned. PostgreSQL itself refuses overlapping active windows; amounts and start dates are frozen by trigger; a new version closes its predecessor; backdating is refused | History cannot be rewritten by staff or by a bug | Built, tested |
| D30 | FX observations are append-only (trigger). A move over 25% is quarantined until staff approve, which adds a NEW row. A rate older than 48 h at message time is refused, never used. Cross rates go through USD only | A bad or stale rate must not silently reprice customers | Built, tested |
| D31 | FX source = WiseCP's own rates via its admin API (read-only key). The adapter fails closed if WiseCP's last refresh is old or missing, if its base currency changes, or if the payload is unexpected. Rate floats are parsed as exact Decimals | One rate authority; WiseCP can stall silently | Built against the documented shape and a MOCK; not yet run against your WiseCP |
| D32 | Every billed message points at an immutable pricing snapshot (rate, FX with source/time, buffer, markup, rounding rule, results). The provider's ACTUAL cost is stored separately from the FX buffer, the fee and the total. Legacy Phase 2 rows got reconstructed snapshots flagged `reconstructed` | Reproducible charges; fixes the buffer-in-cost defect | Built; migration tested with legacy data |
| D33 | Rounding: one half-even rounding per step to the nearest micro-unit; display rounds once, half-up, to the currency's decimals | Unbiased, explainable | Built, tested |
| D34 | A message's lifecycle (sent/delivered/read/failed) is recorded separately from money. Only the configured billable status (default `delivered`) creates a charge, once, because usage is unique per (provider, message id). The default follows Meta's per-delivered-message pricing but is UNVERIFIED against your Chatwoot/Meta payloads | Spec 6.6; four events must never mean four debits | Built, tested |
| D35 | Usage costs are estimates until reconciled. Actuals will be added as separate append-only finalization records (3.9), never by editing usage | History stays reproducible | Planned |
| D36 | The usage endpoint accepts no prices or amounts from callers (unknown fields are rejected). Prices come only from rate cards, FX and the tenant's markup | n8n must not set money amounts | Built, tested |
| D37 | The wallet is never negative. Debt for charges the provider already made is a separate receivable with its own append-only ledger. Funds and debt never coexist (a payment clears debt first), enforced by CHECK constraints. Both ledgers are append-only by trigger | Owner decision (bounded overdraft as an explicit receivable) | Built, tested on PostgreSQL |
| D38 | Provider charges are ALWAYS recorded (any tenant status, any amount). Whether NEW controlled sends are approved depends only on capacity = funds - debt - holds + credit limit. Credit limit defaults to 0 | Recording a charge is not permission to send | Built, tested |
| D39 | Reservations exist only for sends the hub controls, idempotent on the caller's send id, taken under the wallet row lock, converted when the delivered-usage event carries the same send id, released or expired otherwise. A charge with no live hold is still recorded | No double spending; no lost charges | Built, tested |
| D40 | Marketing sends must rest on the tenant's own funds (USD 5 floor, converted), never on credit | Marketing is the riskiest, most expensive category | Built, tested |
| D41 | AI allowance counts ONE message generated by the AI and sent (or about to be) to a customer. Not model calls, tool calls, agent-only drafts or failed generations. The caller claims with a stable key before sending and releases on failure; same key = same count; a released key retried counts once more | Spec section 9; retried workflows must not double-count | Built, tested (PostgreSQL concurrency) |
| D42 | Paid AI packs persist across plan changes; the limit is always plan (or override) + packs, and a downgrade never revokes what was already claimed | A customer who bought a pack should keep it | Built, tested |
| D43 | Manual money changes are requests approved by a DIFFERENT staff member, with a mandatory reason and evidence reference. Kinds: credit funds, take funds back (funds only), write off debt, add a missed charge, reverse one message charge (full, once). A person may approve their own request only below `ADJUSTMENT_SELF_APPROVAL_LIMIT_USD` (default 0), and only when a trustworthy FX rate exists; every such case is flagged | Spec 6.5/14.5; one person must never be able to create or erase money alone | Built, tested |
| D44 | No machine API key can change a wallet by hand. Machine keys can credit (verified payments, Phase 4) and report usage; humans adjust through the staff UI under their Zitadel identity | Attribution to a person | Built, tested |
